# ROOT — Proof of Concept Specification

## 1. Purpose

This POC exists to prove one thing:

> Is it fun to understand a simulated network well enough to attack or defend it using realistic cybersecurity concepts?

The POC is intentionally small.

It does **not** attempt to prove:
- long-term progression
- procedural worlds
- ranked PvP
- co-op
- a persistent internet
- dozens of tools
- full malware simulation
- enterprise-scale identity systems

It only proves the core simulation and interaction loop.

---

# 2. Core POC Experience

The player runs ROOT/OS, a browser-native fictional operating system.

The player can:

- inspect a network
- scan hosts
- inspect open services
- authenticate to machines
- browse a simulated filesystem
- inspect users and permissions
- find weak credentials or exposed secrets
- escalate privileges
- move laterally
- install a simulated persistence agent
- retrieve an objective
- view the resulting telemetry from the Blue Team perspective

The same simulation powers both Red and Blue.

---

# 3. POC Game Modes

## 3.1 Red Team POC

Objective:

> Gain access to `FIN-DB` and retrieve `PROJECT_ATLAS.pdf`.

The player begins outside the target network.

## 3.2 Blue Team POC

Objective:

> Detect and contain a scripted Red Team attack before the protected file is extracted.

The Blue player sees logs and telemetry generated by the same simulation rules.

Every simulated machine is represented by a common structure.

```ts
type Machine = {
  id: string
  hostname: string
  ip: string
  zone: NetworkZone
  os: "linux" | "windows" | "appliance"

  users: SimUser[]
  services: SimService[]
  files: SimFile[]
  processes: SimProcess[]

  permissions: PermissionRule[]
  connections: NetworkConnection[]
  securityControls: SecurityControl[]
```

# 6. Core Simulation Rule

Every player action must create simulation events.

Example:

```text

```

creates:

```text

```

Those events can be consumed by:

- Red result generation
- Blue telemetry
- detection rules
- replay timeline
- scoring

This event-driven design is the backbone of the POC.

# 20. Privilege Escalation POC

This is a core POC mechanic.

DEV-01 contains a simulated service:

```text
backup-sync
```

Properties:

```text
Runs as:
root

Config:
 /etc/backup-sync.conf

Config writable by:
deploy
```

The important reasoning is:

> The player can modify something that a privileged service trusts.

The POC does not need real operating-system exploitation.

It only needs to simulate the relationship.

---

# 21. Privilege Escalation Flow

The player inspects:

```text
ps
```

and sees:

```text
root   backup-sync
```

Then inspects its configuration.

The system indicates:

```text
Owner: root
Writable by group: deploy
```

The player modifies the simulated configuration through an allowed in-game action.

After the service restarts, the player gains:

```text
root@DEV-01
```

Generated events:

```text
PrivilegedConfigModified
ServiceRestarted
PrivilegeChanged
RootSessionCreated
```

Blue telemetry:

```text
deploy modified privileged service config
backup-sync restarted
new root-owned process
```

This proves privilege escalation can be modeled meaningfully.

# 33. Containment Examples

## Revoke Session

Kills a selected active session.

## Reset Password

Invalidates password-based access for that identity.

## Block Connection

Adds a temporary firewall rule.

## Isolate Host

Blocks almost all network connections.

## Remove Persistence

Deletes the selected persistence artifact.

# 54. Server Authority

All meaningful actions are server-authoritative.

Client submits:

```ts
{
  action: "SCAN_HOST",
  targetMachineId: "web-01"
}
```

Server validates:

- is target known?
- is target reachable?
- does actor have required access?
- what events result?
- what Red output is returned?
- what Blue telemetry is generated?

Then state is persisted/broadcast.

# 65. POC Success Criteria

The POC succeeds if testers can answer yes to these.

## Gameplay

- Was discovering the network satisfying?
- Did privilege escalation feel earned?
- Did lateral movement make sense?
- Did Blue feel like investigation rather than whack-a-mole?
- Did the post-match reconstruction reveal something the player missed?

## Learning

After one session, can a beginner explain:

- what a port is?
- what SSH does?
- what privilege escalation means?
- what lateral movement means?
- why valid credentials can still be suspicious?

## Replayability

After finishing Red once, does the player want to try Blue?

After Blue, do they want a human-vs-human version?

If yes, the core concept is validated.

# 68. Definition of Done

The POC is done when a player can:

```text
1. Open ROOT/OS
2. Read the mission brief
3. Discover WEB-01
4. Scan it
5. Gain simulated initial access
6. Find a credential
7. Move to DEV-01
8. Escalate from deploy to root
9. Discover FIN-APP
10. Reach FIN-DB
11. Retrieve PROJECT_ATLAS.pdf
12. Replay the operation from Red, Blue, and Full Truth views
```

And in Blue mode:

```text
1. Observe the same attack
2. Receive realistic telemetry
3. Investigate events
4. Revoke sessions
5. Reset credentials
6. Isolate systems
7. Detect privilege escalation
8. Stop or fail to stop the objective
9. Review the full reconstruction
```

If those two flows are fun, understandable, and coherent:

> ROOT is worth building further.

# 69. Final POC Principle

The POC should never ask:

> Did the player unlock enough hacking power?

It should ask:

> Did the player understand the system well enough to make the right decision?

That is the core of ROOT.
